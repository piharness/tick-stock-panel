# 缓存策略：为什么 Redis 不是这类问题的解

> 2026-11-24。承接 `docs/api-performance.md`（那篇记录的是 12 个"接口超时"的
> 实际根因与修复）。这篇回答一个更前置的问题：**该不该引入 Redis 级的外部缓存**。

## 结论

**不该，至少不是为了这批问题。** 不是因为 Redis 不好，而是因为这次的 12 个症状里
**没有一个是"同一份数据被重复读"** —— 全是"同一个事实被重复**推导**"，以及
"首次调用就要付全价"。缓存改变的是第 2 次及以后，改变不了第 1 次，也改变不了
写入路径。

| 症状 | 真实根因 | 加 Redis 后 |
| --- | --- | --- |
| `/api/kline/minute` 18.9s | `latest_daily_date` 全表枚举 590 个分区 | **0**（首次仍要算 19s） |
| `/api/data/status` 冷 25.4s | 同上 ×2 | **0**（每次失效点都回冷） |
| `decision/score` 24.7s、`case-lab/scan` 29s、`delisting-countdown` 44s | 同一个枚举下游消费 | **0** |
| `/api/intraday/indices` 2.16s | 257 个分区文件 footer | **0** |
| `/api/pipeline/jobs` 112ms | 为 1 条记录重解析 49 个 JSON | 省 ~35ms |
| `/api/citizenship` 528ms | 5.3MB 序列化 84ms + gzip 68ms | 省 ~152ms（唯一明显合适） |
| `/api/kline/minute` 现在 210ms | 真正读盘只有 **18.7ms**，其余是周边聚合 | 缓存响应可省 ~190ms |

只有后两行是"缓存真能救"的，而且都是**响应级**，不是计算级。

补充一个容易忽略的实测：`kline/minute` 端到端 210ms 里，`repo.get_minute()`
（读那 1.7MB 分区、筛出 240 行）只占 **18.7ms**。**只盯数据库/缓存往往修不到
真正的 190ms** —— 那 190ms 是周边派生（昨收、涨跌停价、标的信息）。这也是
"加一层 Redis"最典型的落空方式：加了之后总耗时只掉 19ms。

## 为什么"响应级缓存"也不是根因解

四条硬约束，任何一条都足以否掉它作为**唯一**手段：

1. **首次永远冷。** 用户第一次打开某只股票的图、第一次进某页 —— 那是产品最在意的
   那一次。缓存对这一次没有任何作用。
2. **失效点永远回到冷。** 盘后管道跑完、分区落盘、用户点"更新数据"，缓存必须失效；
   失效后的第一个请求又付全价。而这个仓库的数据一天要落好几次。
3. **写路径零帮助。** "同步数据超时"是逐分区写 + I/O，不是读。Redis 对写路径
   完全无关。2026-11-24 那次 `daily_pipeline` 每次遍历 5,315 个分区导致静默 30 分钟
   I/O、被 stall reaper 杀掉 —— 这类问题加十个缓存也修不掉。
4. **引入仓库最怕的失败模式：假绿。** 缓存与真值不一致时，页面会显示"数据已最新"。
   这个仓库为此专门写过教训（2026-11-23 `maintenance._kline_last` 只看一张表，
   把"管道半途失败"显示成"已最新"，手册拿旧 ETF 必然报错，点多少次都是同一个错）。
   所以凡是**会驱动"是否需要更新"判定的值**，宁可算，也不许缓存陈旧。

## 真正对应的解法：写时维护的目录（catalog），而不是读时填充的缓存

区分两件事：

- **Cache**：读时填充。冷的时候付全价，失效后重新付。
- **Catalog**：写时维护。任何时刻读都是 O(1)，因为它不是"记住上次算的结果"，
  而是"数据写入时顺手记一笔"。

这次的根因恰好属于后者的范畴：`list_partition_dates` 在回答"这张表覆盖了哪些
交易日"，而**写入方本来就知道**自己写了哪一天。

建议的形态（还没做，需要单独评审）：

```
data/_cache/catalog.sqlite
  table_catalog(table TEXT, partition TEXT, dates TEXT, rows INT, max_date TEXT,
                updated_at TEXT, PRIMARY KEY(table, partition))
```

- 写入方在 `_write_partition_locked` / `replace_with_retry` 成功后 upsert 一行（~1ms）；
- `list_partition_dates` 变成一条索引查询（O(1)）；
- `latest_daily_date` / `latest_minute_date` 变成 `SELECT max(max_date)`；
- 指纹不匹配时（外部脚本写入 / catalog 缺失）走一次全量重建，并原子替换；
- SQLite 是 Python stdlib，**PyInstaller 打包与单容器部署都不增加依赖**。

预期收益：19,000ms → 亚毫秒；`enriched` 那 32ms 也归零；而且**冷启动第一次就是快的**
（这也是 catalog 与 cache 的本质差别）。

风险与代价（诚实部分）：要覆盖 8 类写路径（日K月分区、enriched 日分区、分钟、
ETF、指数、adj_factor、财务、外部导入），漏一处就是"目录说没有、其实有"。
所以它必须先有一个"对账"入口：定期用真扫一遍校验 catalog，不一致就重建 + 告警。
**这是它比 Redis 贵的地方** —— 贵在正确性工程，不在部署。

## 什么条件下才该上 Redis

三个条件同时成立时才值得：

1. **多进程/多实例共享**同一个缓存（现在是单进程 + 单容器，桌面版是单 exe，不成立）；
2. 跨请求复用**昂贵结果**（citizenship 的 5.3MB 序列化字节，成立）；
3. 能接受"缓存落后于真值"的产品语义（只对展示型数据成立）。

当前只满足第 2 条。而**只为了第 2 条，进程内 LRU + 预序列化字节就够了**：
citizenship 5.3MB → gzip 后 1.1MB，缓 3 天也就 3.3MB 内存 / 磁盘，比多一个
外部服务的运维与打包成本低一个量级。

如果将来真的多实例（比如给多人共用一台服务器），那时 Redis 的边际成本才会低于
自己实现跨进程失效，届时再上，并且**先上响应级**（预序列化字节 + ETag），
不要试图用它承载"目录"职责 —— 那需要持久化与对账，Redis 不是干这个的。

## 已经落地执行机构（"杜绝以后再犯"的部分）

光有结论没有用，所以这次同时把规则做成了会红的断言：

1. **`backend/tests/test_thin_api_scan_guard.py`** —— 两条规则，CI（`uv run pytest tests -q`）会跑：
   - 规则 A：`app/` 下任何地方对**月分区表**（`MONTHLY_DAILY_TABLES`，随定义自动同步）
     调 `list_partition_dates` / `partition_date_map` 即失败，无白名单；
   - 规则 B：`app/api/**` 里的这类调用按 (文件, 函数) 登记棘轮，**新增调用点直接失败**，
     现存 5 处都在日分区表上并写明实测耗时。
   - 做过负控：故意写一个违规端点，两条规则都变红；删掉后恢复绿。
2. **`scripts/probe_api_latency.py --compare baseline.json`** —— 33 个界面端点的
   中位数对比基线，劣化超 50%（且有 30ms 绝对地板）即非零退出。负控验证过会报
   并返回退出码 1。
3. **判据清单**（写新接口时逐条过）：
   - 「从全部历史算一个数」的操作，要么写入时维护，要么读时只碰 O(1) 的位置；
   - 分区表能靠**文件名**回答的问题，不要打开 parquet；
   - 缓存只允许缓存「文件 + 签名的纯函数」；会让页面判「已最新」的值一律不许缓存陈旧；
   - 新端点必须在 probe 里加一行，并写明它属于哪一档预算（500/1200/8000ms）。

## 下一步（按性价比排序）

1. **写时 catalog**（上面那个 SQLite）—— 把 19s 的冷路径彻底消灭，是这批问题里
   唯一还残留"首次也慢"的地方；
2. **响应级缓存 + 预序列化**给 `citizenship`（152ms）与 `kline/minute`（~190ms），
   进程内 LRU 即可，不上外部服务；
3. **任务化** `crowding-verdict`（冷启动首次 30.8s）：提交 → 轮询进度，而不是阻塞请求。
   这是"慢接口"的最后一种形态，只能靠改交互语义解决，缓存和目录都救不了。

## 执行记录（2026-11-24，三项已落地）

### ① 写时目录：交易日历增量合并

**先说清楚真正的残留成本在哪**。`trading-days-warm` 启动预热早就存在，所以
"进程刚起来第一次"不是问题。真正的重复成本是：指纹包含**当月月分区的 mtime**，
而盘后管道**每个交易日**都会重写当月分区 ⇒ 指纹必变 ⇒ `kline_trading_days`
全量重扫 590 个分区（19,043ms），并且落在写入之后**第一个读请求**上。
这是每天一次，预热救不了。

做法：写入方本来就知道自己写了哪些日期（`merged["date"]`），加一条通知通道
`trading_days.note_partition_dates(data_dir, table, days)`，把已知日期并进缓存，
并用**当前目录状态**重算指纹（一次 readdir + 几个 stat）。接在
`repository._write_partition_locked` 这个唯一收口上。

- 新增成本：**8.6ms/次**（readdir 5.2 + 指纹 3.4，实测 590 个分区）
- 省掉：**19,043ms/交易日**
- 保守边界：只处理月分区表；**没有内存底稿就不合并**（返回 False，交给正常路径）；
  只做并集不做删除，目录被删时指纹自然不匹配、自动全量重算。
- 顺带把最后一个请求路径上的调用点（`decision/bars.sessions()`，8 个调用方、
  其中一个在 `/api/decision/*` 首屏）接到同一个缓存源。

### ② 响应级缓存：预序列化 + 整份响应

- **`citizenship`**：dict 缓存命中后计算是 0ms，但每次请求仍要 `json.dumps` 84ms
  + gzip 68ms（5.3MB → 1.1MB）。改成缓存 `(原文字节, gzip 字节)` 两份，按
  `(data_dir, as_of)` 分键，端点直接返回 `Response` 而不让框架再序列化一遍。
  **404.7ms → 19.8ms**。
- **`kline/minute` 历史日**：端到端 210ms，其中真正读盘只有 18.7ms，其余散在
  标的信息/昨收/涨跌停价/序列化上——逐个猜不如整份缓存。只在
  `trade_date < today` 时缓存（当日每分钟在变、`live=true` 要绕过本地）。
  **~500ms → 11ms**。
- 有了共同底座 `app/services/ttl_cache.py`（有界 LRU + TTL + 单飞）。

### ③ `crowding-verdict`：修正上一轮的判断

上一轮我写的是"只能靠改交互语义（任务化）解决"。**这条判断不准确**，实测后改成
**stale-while-revalidate**：数据写入时只打脏标记，下一次读**返回旧值**并顺手起一个
后台重算。于是读路径永不阻塞，最坏是看到昨天的静态统计 —— 而这个结论本来就是
"换手率 → 后续 20 日超额"的历史统计，晚一天没有代价。

任务化（202 + 轮询）能解决阻塞，但要求前端多一套状态机；这里不需要。
另外把原来 30 分钟的 TTL 去掉了 —— TTL 的真正问题是**每半小时就有一个请求
同步等 35s**，等于把一次等待变成每天四十八次。

配套：启动预热（`crowding-warm` 线程，实测后台 40s 算完，抢在用户之前）。
**35.4s（冷）→ 5.8ms**，且不再有 TTL 悬崖。

### 复测（同一把尺子，36 个端点 × 3 次）

```
36 端点 | 中位数最差 246ms | 超预算 0 个
对比基线（20:22）: 无劣化
```

`/api/citizenship` 404.7ms → **19.8ms**；`crowding-verdict` 3.7ms；本地历史分钟图 10.2ms。

### ④ 拆 `decision/overview`：同一批文件被读了 3~4 遍

首屏 302ms，拆开后（容器内实测）：

| 段 | 耗时 | 问题 |
| --- | --- | --- |
| `ledger.load_cards` | 42.7ms | 被它自己与 `ledger_health` 各调一次 |
| `settle.outstanding` | 49.3ms | 内部又调 `load_cards` + `load_settlements` |
| `ledger.ledger_health` | 57.1ms | 又扫一遍 settlements，还把整份文件 `read_text` 数行数 |
| `settle.score` ×2 | 1.3ms | 无问题 |

一份 283KB 的 `settlements.jsonl` 被逐行解析三遍、整读一遍。

改法：给 `ledger` 的两个纯读取函数加**文件签名缓存**（cards 用一次 `os.scandir`
取 (名字, mtime, 大小)，settlements 一次 `stat`）。三条纪律：

- **不缓存异常**：账本损坏时每次重新读、重新抛，绝不把 `LedgerCorruptError`
  变成"记住的结论"；
- **返回 list 副本**，行 dict 保持共享只读 —— 调用方会排序/切片，共享同一个 list
  迟早被就地改坏（全仓确认没有调用方就地改卡片/结算行）；
- `ledger_health` 的非空行数改为 `len(rows) + len(problems)`：`_scan_settlements`
  对每个非空行要么收进 rows、要么记一条 problem，二者一一对应。省掉第二次全量
  `read_text`，并把这个恒等式写成测试。

**302ms → 124ms**。剩下的主要是 `gates.evaluate` 里的四条门禁检查
（`check_k4_fresh` 26ms、`bars.latest_session` 24ms、k3 17ms、k2 16ms）——
**这些是"数据是否新鲜"的判定，必须新鲜，不该缓存**。到此为止是对的。

### ⑤ 结论物化：冷进程也不再等 30.8s

③ 的 stale-while-revalidate 解决了"稳态不阻塞"，但**进程内缓存只在本进程活着时
有效**：重启后第一次读仍要同步算一遍，启动预热只是抢在用户之前（进程刚起的那几秒
打开页面仍会撞上）。

把结论落盘到 `data/_cache/crowding_verdict.json`（1.1KB，带 version / built_at /
n）。读取顺序变成：进程内 → 磁盘快照 → 同步计算。前两级都是 O(1)。

**验证方式**：`docker restart`（只重启进程，不重建镜像）后立刻打端点 ——
**16ms**，而不是 35.4s。这是"物化"与"缓存"的本质差别：前者让冷启动也不需要重算。

配套：`clear_crowding_cache()` 用**内存标记**让快照失效，而不是删文件 ——
删除要走 `unlink`，在本仓的沙箱策略下会被拦，而"清缓存"不该依赖删除权限。

### ⑥ `dragon-tiger`：当日不落盘，于是每个请求都去问 provider

246ms 的本体不是解析，是**取数策略**：

- 历史日有磁盘缓存（`data/dragon_tiger/date=YYYY-MM-DD.json`），命中 1.2ms；
- 但**当日不落盘**（`actual < today` 才写，设计如此：盘中回退与盘后补充都以现拉
  为准）。于是从收盘到 `pull_latest` 增量任务跑完这段窗口里，每次请求都实时拉
  三榜：**158ms/次**，而这个端点一周被调 113 次、页面是 15s 级轮询。
- 另外 `_local_trading_days` 被调了两次（一次解析 `target=None`，一次在
  `resolve_trade_date` 内部），每次都是一遍 readdir + 指纹（9~31ms）。

改法两处，都不动"当日以现拉为准"这条语义：

1. `resolve_trade_date(..., days=...)` 接受调用方已取好的日历，避免同一份日历
   算两遍；
2. 当日结果进 **60s 进程内缓存**（复用 `ttl_cache`）。60s 足够吸收 15s 轮询的
   重复，又短到不会让"刚发布"被长时间遮蔽；`source_unavailable` 也一起缓存，
   否则未配置 provider 时每次都要重建插件注册表。

**246ms → 18ms**（TTL 到期后第一发 176ms 是真实拉取）。历史日路径未变，仍是
磁盘缓存 21ms。

### 仍然没解决 / 不该用缓存解决的

- **`gates.evaluate` 87ms**（overview 的主体）：四条门禁判断"数据新不新鲜"，
  缓存它们等于让门禁对陈旧数据放行。这是设计约束，不是性能缺陷。
- **`/api/kline/minute?symbol=600519.SH` 174ms**：本地分钟分区里没有这只票的
  当日数据，走 live 兜底，每次都要问上游 —— **数据覆盖问题，不是性能问题**。
  本地有历史分钟数据的标的（如 `000001.SZ`）命中缓存只要 10ms。
- **`/api/decision/slate` 100ms**：下一个值得拆的（与 overview 同源，也是多次
  读同一批账本）。
